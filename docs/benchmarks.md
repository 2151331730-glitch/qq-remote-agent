# 压测报告

> 硬件：ROG 枪神 8（i9-14900HX / 32GB / Windows 11）。全部用 `tests/stub_claude.py` 假 CLI，
> 每次模拟 200ms 执行耗时，**不消耗任何模型额度**，测的是队列与调度本身。

## 1. 单机 SQLite 队列

场景：一次性提交 40 条任务，`stub_sleep=0.2s`，测到全部落库为止。

| 场景 | 墙钟 | 吞吐 | 排队等待 p95 | 单任务执行 p95 |
|---|---|---|---|---|
| 1 worker · 同一目录 | 14.15s | 2.83 条/秒 | 12.6s | 358ms |
| 4 worker · 同一目录 | 13.88s | 2.88 条/秒 | 12.3s | 348ms |
| 4 worker · 不同目录 | **3.94s** | **10.15 条/秒** | 2.6s | 474ms |

**结论**：

1. 4 个 worker 跑同一目录**没有加速**（2.83 → 2.88）——这是刻意的：同目录并发改文件会互相踩，
   `cwd` 锁把并行度压回 1。这条数据同时证明了"锁是生效的"，不是摆设。
2. 不同目录时 4 worker 拿到 **3.6 倍**吞吐。单任务只占 200ms，瓶颈在进程创建与调度，
   所以拿不到线性 4 倍。
3. 排队等待 p95 从 12.6s 降到 2.6s，说明在突发提交下队列积压被有效摊平。

### 一次真实的优化

第一版实现是"先 claim 再发现目录锁被占 → 放回队列 → 睡 1 秒"，
不同目录场景只有 **5.16 条/秒**。改成在 SQL 里直接跳过已锁目录（`claim_next(exclude_cwds=...)`）后
提升到 **10.15 条/秒**，接近 2 倍。日志里能直接看到每条任务的状态翻转少了一轮。

## 2. 多进程共享 Redis 队列

场景：两个 bridge 进程（各 2 worker，共 4 个执行槽）连同一个 Redis，40 条任务各从一半的看板提交。

```
提交 40 条 → 4.94 秒跑完，8.09 条/秒
A 进程完成 20 条，B 进程完成 20 条
状态分布：succeeded 40，无重复、无丢失
```

**结论**：跨进程消费成立——两个进程从同一个 `ZSET` 抢任务，Lua 脚本保证"检查状态 + 改状态 + 出队"
是一个原子操作，所以既不重复执行也不漏。多机部署只需要把它们指向同一个 Redis。

## 4. 已知边界

- 单任务执行耗时是假 CLI 的 200ms；真实任务受模型延迟支配（实测 8–60 秒），
  所以真实场景的吞吐约为 `worker 数 ÷ 平均任务时长`，压测数字只反映调度开销。
- 没有做持续压测（小时级）和内存曲线，队列积压只测到 40 条。

## 5. Redis 哨兵故障转移实测

拓扑：6380 主 / 6381 从 + 三个哨兵（26380-26382，quorum=2，`down-after` 3000ms）。

| 阶段 | 结果 |
|---|---|
| 写入 5 条任务（认领 2、完成 1） | 正常 |
| 关闭主库（`shutdown nosave`） | — |
| 哨兵选出新主 | **4.6s** |
| 客户端首次写入成功 | **5.6s**（选举后约 1 秒） |
| 数据 | 5 条任务 + 1 条完成记录都在，队列深度 4，可继续认领 |

**优化过程**：第一次测是 **31 秒**才恢复写入。查到两处：
1. redis-py 内置指数退避重试（默认 3 次，合计约 7 秒/次调用）→ 关掉，改由自己的重连层立刻重连
2. 故障窗口里会短暂连到已降级的旧主，写操作报 `READONLY` → 识别后重新发现主库

改完从 31s → 20s → **5.6s**。剩下的 1 秒是"哨兵选完主"到"客户端发现"的固有延迟。

已知边界：Redis 是异步复制，主库在最后一刻写入但未同步的数据仍可能丢（本测试数据没丢，但这是概率问题，不是保证）。
